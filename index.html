01. Network reconnaissance

Identify public website/domain details, review security logs, and understand TTL.

AimDNS / WHOISLogsTTL

Aim

To collect publicly available information about an authorized college website and identify critical warnings in local security logs.

Algorithm

  1. Confirm the official domain with the college.
  2. Query DNS records and domain registration details.
  3. Review the system's own security logs for critical events.
  4. Record findings, time, tool, and evidence without exposing private data.
  5. Check TTL using ping and explain its meaning.

Website / DNS details

# Replace with the official domain
nslookup college.example
nslookup -type=MX college.example
nslookup -type=NS college.example
whois college.example

# Linux/macOS: common DNS records
dig college.example A
dig college.example AAAA
dig college.example MX
dig college.example NS
dig college.example TXT

Security logs

# Linux: systemd journal, recent errors
sudo journalctl -p 0..4 --since "24 hours ago"

# Ubuntu/Debian authentication log
sudo grep -Ei "critical|alert|failed|invalid|denied" /var/log/auth.log

# Windows PowerShell: recent critical/error events
Get-WinEvent -FilterHashtable @{
 LogName='System'; Level=1,2; StartTime=(Get-Date).AddDays(-1)
} | Select-Object TimeCreated, Id, ProviderName, Message

What to write about critical warnings

  • Repeated failed logins: may indicate password guessing; verify source and account.
  • Privilege escalation / unexpected admin activity: verify against approved change records.
  • Service crash or repeated restarts: investigate the service logs and recent updates.
  • Firewall blocks / malware alerts: preserve timestamps and event IDs; follow the incident process.
TTL: Time To Live is a limit on a packet's lifetime, reduced by each router hop. On Windows, ping -4 www.google.com displays the reply's remaining TTL. On Linux/macOS use ping -c 4 www.google.com. The returned value varies by destination, route, OS, and time; record your actual result instead of assuming a fixed Google TTL.

02. Detect MAC / ARP changes with arpwatch

Monitor a network you administer for unexpected IP-to-MAC mapping changes.

AimARP monitoringLinux

Aim

To use arpwatch to log changes in IP-to-MAC address mappings and investigate possible ARP spoofing.

Algorithm

  1. Get permission and identify the correct lab interface.
  2. Install arpwatch from the operating system's trusted package repository.
  3. Start monitoring the authorized interface.
  4. Review logs for “changed ethernet address” or “flip flop” events.
  5. Verify suspicious changes against router/DHCP records; a change is not proof by itself.
# Debian / Ubuntu
sudo apt update
sudo apt install arpwatch

# Find the interface (example: enp0s3 or eth0)
ip -br link
ip route

# Start monitoring ONLY the approved lab interface
sudo arpwatch -i enp0s3

# Check common log locations
sudo journalctl -u arpwatch --since "1 hour ago"
sudo grep -Ei "changed ethernet|flip flop|new station" /var/log/syslog
If the service is not named arpwatch or uses a different log file on your distribution, check systemctl status arpwatch and your distribution's package documentation. Do not generate spoofed ARP traffic on a shared college network.

Evidence to submit

Screenshot the command, monitoring status, and any relevant alert with MAC addresses partly redacted. If there are no alerts, write “No suspicious mapping change observed during the test window.”

03. Vulnerability assessment with Nessus

Use the Nessus interface to run an approved, non-destructive assessment and document findings.

AimNessusReport

Aim

To assess an authorized lab host for known vulnerabilities and classify findings by severity.

Algorithm

  1. Obtain written scope and target IP from the instructor.
  2. Install/launch Nessus and complete activation if required.
  3. Create a new scan; select Basic Network Scan or the instructor-approved template.
  4. Enter only the approved lab target and run the scan.
  5. Review Critical/High findings, validate them, and export a report.

Procedure / proof

  1. Open the Nessus web interface shown by your installation.
  2. Choose New Scan → Basic Network Scan.
  3. Set a clear name, such as Authorized-Lab-Assessment.

Report format: Finding | Severity | Evidence | Business impact | Recommended fix | Retest result. A scanner finding should be validated before calling it a confirmed vulnerability.

04. IP address and hop count with traceroute

Trace the route to Microsoft and your college website, then record the final responding hop.

Aimtraceroute / tracert

Aim

To resolve a hostname to an IP address and observe the network hops toward that destination.

Algorithm

  1. Resolve the website hostname to an IP.
  2. Run traceroute/tracert.
  3. Count numbered hop rows; note timeouts as non-responding hops, not necessarily failures.
  4. Repeat at a different time if needed and record the date.

Windows

nslookup www.microsoft.com
tracert -d www.microsoft.com

nslookup college.example
tracert -d college.example

Linux / macOS

getent ahosts www.microsoft.com
traceroute -n www.microsoft.com

getent ahosts college.example
traceroute -n college.example
If traceroute is not installed, install it through your OS package manager or use the tool approved by your instructor. Routes may change, and some routers do not respond to traceroute probes. Report the observed result, not a guessed hop count.

05. Buffer overflow concept — safe local demonstration

Learn how writing past a fixed-size buffer is a memory-safety bug. Use a bounds-checked example; do not attack another process or service.

AimCMemory safety

Aim

To demonstrate a buffer boundary problem conceptually and show how length validation prevents it.

Algorithm

  1. Create a fixed-size character buffer.
  2. Read user input with a bounded input function.
  3. Check whether the input was too long.
  4. Print the accepted text and explain that unchecked writes can corrupt adjacent memory.
// safe_buffer.c — safe bounds-checked demonstration
#include 
#include 

int main(void) {
    char buffer[16];

    printf("Enter text (maximum 15 characters): ");
    if (fgets(buffer, sizeof buffer, stdin) == NULL) {
        return 1;
    }

    size_t n = strlen(buffer);
    if (n > 0 && buffer[n - 1] == '\\n') {
        buffer[n - 1] = '\\0';
    } else {
        int ch;
        while ((ch = getchar()) != '\\n' && ch != EOF) { }
        printf("Input was too long; extra characters were discarded.\\n");
    }

    printf("Accepted input: %s\\n", buffer);
    return 0;
}
# Compile and run locally
gcc -Wall -Wextra -fstack-protector-strong safe_buffer.c -o safe_buffer
./safe_buffer
Explanation for viva: A classic buffer overflow occurs when a program writes more bytes than a buffer can hold. This example intentionally avoids an unsafe exploit and demonstrates a safe fix using fgets() plus input-length handling.

06. Block and unblock port 8080

Demonstrate a firewall rule on your own lab machine and verify it. Keep an alternate admin session open when changing firewall rules remotely.

AimFirewallVerification

Aim

To block inbound TCP traffic to port 8080, verify the rule, and then remove the rule to unblock it.

Algorithm

  1. Check whether the service is listening on port 8080.
  2. Add a firewall block rule for inbound TCP 8080.
  3. List the rule and test from an authorized second machine.
  4. Remove the rule and retest.

Ubuntu with UFW

# Block inbound TCP 8080
sudo ufw deny 8080/tcp
sudo ufw status numbered

# Unblock: remove the matching rule
sudo ufw status numbered
sudo ufw delete deny 8080/tcp

# Check local listener
sudo ss -lntp | grep ':8080'

Windows PowerShell (Admin)

# Block inbound TCP 8080
New-NetFirewallRule -DisplayName "Lab Block TCP 8080" -Direction Inbound -Protocol TCP -LocalPort 8080 -Action Block

# Verify rule
Get-NetFirewallRule -DisplayName "Lab Block TCP 8080"

# Unblock by removing the lab rule
Remove-NetFirewallRule -DisplayName "Lab Block TCP 8080"

# Check local listener
Get-NetTCPConnection -LocalPort 8080 -State Listen
A firewall rule blocking inbound traffic does not necessarily stop a service listening locally, and a local connection test alone may not prove remote blocking. Record the firewall rule plus a test from an authorized second machine.

07. Identify suspicious traffic with Snort

Use Snort as a network intrusion detection system (IDS) on an authorized lab interface, inspect alerts, and remove it only if your instructor asks.

AimIDSAlerts

Aim

To run Snort in detection mode, review generated alerts, and demonstrate clean uninstallation in a disposable lab environment.

Algorithm

  1. Install Snort from the trusted OS repository.
  2. Identify the correct lab interface and verify the configuration.
  3. Run a short detection session or use the instructor-provided PCAP.
  4. Review alerts and map them to timestamps and rule IDs.
  5. Stop Snort, then remove it only from your own lab machine if required.
# Debian / Ubuntu — install
sudo apt update
sudo apt install snort

# Find interface
ip -br link

# Validate configuration (path/options can vary by version)
sudo snort -T -c /etc/snort/snort.conf

# Run IDS on an authorized lab interface (classic Snort 2 syntax)
sudo snort -A console -q -c /etc/snort/snort.conf -i enp0s3

# Review alerts in another terminal; common Snort 2 location
sudo tail -f /var/log/snort/alert

Remove Snort (only from your own disposable lab)

# Stop service first (service name may vary)
sudo systemctl stop snort 2>/dev/null || true

# Remove package but keep config
sudo apt remove snort

# Optional: purge config only if you are sure you no longer need it
# sudo apt purge snort
Do not uninstall security monitoring from a college or workplace system without the administrator's approval. Snort is an IDS; it detects suspicious patterns and alerts, but does not automatically prove that a host is vulnerable.

09. Vulnerability assessment with OWASP ZAP

Assess a deliberately vulnerable training app or your own local web app. Begin with passive scanning; active scans send attack-like requests.

AimOWASP ZAPWeb security

Aim

To assess a web application for common security issues using OWASP ZAP and document risk and remediation.

Algorithm

  1. Get written authorization and define the target scope.
  2. Start ZAP and open the training app (prefer localhost or a deliberately vulnerable app).
  3. Browse the app through ZAP to build the site tree.
  4. Review passive alerts first.
  5. Run an active scan only on an explicitly authorized test target.
  6. Export the report, validate findings, and suggest fixes.

GUI procedure

  1. Install OWASP ZAP from its official project website.
  2. Choose the automated scan option only for a permitted training target.
  3. For a safe first pass, browse the application through ZAP and inspect the Alerts tab.
  4. Record alert name, risk, URL, evidence, and remediation.
  5. Export an HTML report for your practical record.
Common checks: missing security headers, cookie flags, mixed content, information disclosure, and input-validation alerts. Treat scanner results as leads that require manual verification.

Practical record checklist

  • ☐ Aim and algorithm for each experiment
  • ☐ Commands / settings used and date/time
  • ☐ Screenshot of tool and output
  • ☐ Findings, severity, evidence, and remediation
  • ☐ Scope / permission noted; sensitive values redacted
  • ☐ Conclusion: what was observed and what was not verified

This page is a study guide, not a claim that any scan has been run. Tool versions, paths, interface names, and command options vary by operating system.
