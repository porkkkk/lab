02. Detect ARP spoofing using ARPwatch

Source notes: Experiment 2

AimARP monitoringLinux

Aim

To install and run ARPwatch and inspect logs for unexpected IP-to-MAC address changes.

Algorithm

  1. Update the package list and install arpwatch and rsyslog.
  2. Enable and check the logging service.
  3. Identify the actual network interface using ip link show.
  4. Start arpwatch for the correct interface.
  5. Inspect logs and verify any alerts against trusted router/DHCP records.
sudo apt update
sudo apt install arpwatch -y
sudo apt install rsyslog -y
sudo systemctl enable --now rsyslog
sudo systemctl status rsyslog

# Find your actual interface; it may not be eth0
ip link show

# Use the interface name that exists on your system
sudo systemctl enable --now arpwatch@eth0.service
sudo systemctl status arpwatch@eth0.service
sudo grep -i arpwatch /var/log/syslog
Replace eth0 if your interface has a different name (for example, enp0s3). A changed MAC mapping can have legitimate causes, so treat an alert as a lead to investigate—not proof of spoofing.

Conclusion template

“ARPwatch was installed and its service/logs were checked. During the observation period, [write the alert found / no suspicious mapping change was observed].”

04. Buffer overflow demonstration

Source notes: Experiment 4 · C language

AimCMemory safety

Aim

To understand how writing more input than a fixed-size buffer can safely hold may cause memory corruption, and to demonstrate a bounds-checked alternative.

Algorithm

  1. Declare a character buffer with a fixed size.
  2. Prompt the user for a name.
  3. Read input with a length-limited function.
  4. Display accepted input and explain why unbounded input is unsafe.
// buffer_demo.c — safe classroom demonstration
#include 
#include 

int main(void) {
    char name[20];

    printf("Enter your name (maximum 19 characters): ");
    if (fgets(name, sizeof name, stdin) == NULL) {
        return 1;
    }

    size_t n = strlen(name);
    if (n > 0 && name[n - 1] == '\\n') {
        name[n - 1] = '\\0';
    } else {
        int ch;
        while ((ch = getchar()) != '\\n' && ch != EOF) { }
        printf("Input was too long; extra characters were discarded.\\n");
    }

    printf("Hello %s\\n", name);
    return 0;
}
nano buffer_demo.c
gcc -Wall -Wextra -fstack-protector-strong buffer_demo.c -o buffer_demo
./buffer_demo
Viva: The original note uses scanf("%s", name) with char name[20] and no maximum width. That is unsafe for long input. This page uses fgets() to demonstrate the concept without intentionally triggering a crash. A segmentation fault is not guaranteed or a reliable test.

05. Install and uninstall Snort IDS

Source notes: Experiment 5

AimSnort IDSLinux

Aim

To install Snort, verify its version/configuration, run it on an authorized lab interface, and remove the package from a disposable lab system when required.

Algorithm

  1. Update package lists and install Snort.
  2. Check the installed version and configuration directory.
  3. Test the configuration using the config file appropriate for the installed version.
  4. Identify the authorized lab interface and run Snort in monitoring mode.
  5. Stop Snort, then uninstall it only if authorized.
sudo apt update
sudo apt install snort -y
snort -V
ls /etc/snort

# Confirm which config file exists on your version
ls /etc/snort/snort.*

# The notes use Snort 3-style Lua configuration:
sudo snort -T -c /etc/snort/snort.lua

# Find the real interface name first
ip link

# Run only on an authorized lab interface
sudo snort -c /etc/snort/snort.lua -i eth0

# Optional basic connectivity test
ping -c 4 8.8.8.8

# Remove from your own lab machine only
sudo apt purge snort -y
sudo apt autoremove -y
Snort 2 and Snort 3 use different configuration formats and options. If snort.lua is absent, do not assume the command will work; inspect your installed version and package documentation. Avoid removing monitoring software from managed systems.

06. Study logs and registries

Source notes: Experiment 6 · Windows and Linux

AimEvent logsRegistry

Aim

To inspect operating-system logs for login/account events and review Windows startup Run keys.

Algorithm

  1. Open Event Viewer in Windows and inspect the Security log.
  2. Search for the listed event IDs and note time, account, and outcome.
  3. Inspect startup Run registry keys without changing them.
  4. On Linux, review authentication logs and journal entries.
  5. Record suspicious events with context; redact usernames and IPs in shared reports.

Windows

# Win + R, then enter:
eventvwr.msc

# Event IDs in the notes
4624  Successful logon
4625  Failed logon
4720  User account created
4726  User account deleted
1102  Security audit log cleared

# Win + R, then enter:
regedit

# Inspect these keys (do not edit without authorization)
HKEY_CURRENT_USER\\Software\\Microsoft\\Windows\\CurrentVersion\\Run
HKEY_LOCAL_MACHINE\\SOFTWARE\\Microsoft\\Windows\\CurrentVersion\\Run

Linux

ls /var/log
sudo less /var/log/auth.log
sudo tail -n 30 /var/log/auth.log
sudo grep -a -i "failed" /var/log/auth.log
sudo grep -a -i "authentication failure" /var/log/auth.log
sudo grep -a -i "failed password" /var/log/auth.log

journalctl
sudo journalctl | grep -i "authentication"
sudo journalctl | grep -i "failed"
sudo journalctl -n 30
Some Linux distributions use different authentication log paths or only the systemd journal. Event IDs need context: a failed login alone does not prove an attack, and event 1102 is important because it indicates the Security audit log was cleared.

07. Create firewall rules using iptables

Source notes: Experiment 7

AimFirewallLinux

Aim

To inspect firewall rules, create example ACCEPT and DROP rules, save a rules snapshot, and review kernel logs.

Algorithm

  1. List current rules and counters.
  2. Add an ACCEPT rule for inbound TCP port 80 in the lab.
  3. Add a DROP rule for inbound TCP port 23 in the lab.
  4. List rules with line numbers and save a snapshot.
  5. Check logging and remove temporary rules after the experiment if required.
# Inspect current rules
sudo iptables -L -n -v

# Example lab rules (run only on a machine you administer)
sudo iptables -A INPUT -p tcp --dport 80 -j ACCEPT
sudo iptables -L INPUT -n
sudo iptables -A INPUT -p tcp --dport 23 -j DROP
sudo iptables -L INPUT -n -v --line-numbers

# Save a snapshot to a local file
sudo iptables-save > firewall.rules
cat firewall.rules

# Add logging at the end of INPUT (can generate many logs)
sudo iptables -A INPUT -j LOG --log-prefix "IPTABLES: "
sudo journalctl -k | grep IPTABLES
Be careful when changing firewall rules over SSH; you can lock yourself out. These rules affect inbound traffic and may be overridden by other rules or firewall managers. The source note's ping command tests connectivity, not whether a particular TCP port is blocked.

Optional cleanup

# List numbered INPUT rules, then delete only the rule you added:
sudo iptables -L INPUT -n -v --line-numbers
# Example only: replace N with the verified rule number
sudo iptables -D INPUT N

08. Demonstrate an intrusion detection system

Source notes: Experiment 8 · Snort custom ICMP alert

AimSnort ruleICMP

Aim

To configure a local Snort rule that alerts on ICMP traffic and observe alerts in an authorized lab.

Algorithm

  1. Install Snort and verify the version and available config files.
  2. Validate the installed configuration.
  3. Create a local rule with a unique SID.
  4. Run Snort on the approved lab interface using that rule.
  5. Generate benign ICMP traffic only within the authorized lab and inspect alerts.
sudo apt update
sudo apt install snort -y
snort -V
ls /etc/snort

# Validate only if this config exists for your installed version
sudo snort -T -c /etc/snort/snort.lua

nano ~/test.rules

Create this rule in ~/test.rules:

alert icmp any any -> any any (msg:"ICMP TEST ALERT"; sid:1000001; rev:1;)
# Snort 3 options differ from Snort 2; check `snort --help`
# and your version's documentation before running.
sudo snort -c /etc/snort/snort.lua -R ~/test.rules -i eth0 -A alert_fast

# Source notes' simple test:
ping -c 4 8.8.8.8
The source notes combine a Lua configuration (Snort 3) with command-line options that may vary by version. Confirm the installed Snort version and use its documented syntax. Use a local test host if external ICMP traffic is not permitted.

Evidence

Capture the alert message, SID 1000001, timestamp, and the test traffic used. The alert indicates that the rule matched traffic; it is not by itself proof of a compromise.
